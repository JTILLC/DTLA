## Why Tru Infusion isn't on the calendar for 8/5/26

**Two independent causes. The work is recoverable.**

### 1. The visit was never saved to the cloud — and was then reset

The calendar can only draw what's in Firestore. Reading the full cloud list (Open… in the timesheet app, sorted newest-first):

- The newest document of any kind is **Quincy Foods "081225", saved 8/6/2026 9:39 AM**.
- The most recent **Tru Infusion** documents are `052325` and `060325`, both saved **12/13/2025**. Nothing since.

So there is no Tru Infusion visit for 8/5/26 to show. The timesheet app's own recovery list says what happened to it:

```
Reset — Tru Infusion        8/5/2026, 7:44:29 PM — 6 days
```

Six days of Tru Infusion work were on screen, unsaved, when Reset was used. The snapshot taken before that reset is still there.

**To get it back:** timesheet app → **⋯ → Recover unsaved work…** → restore **"Reset — Tru Infusion, 8/5/2026, 7:44:29 PM — 6 days"**. Then pick the customer and press **Save** so it reaches the cloud — that's the step that puts it on the calendar. (Restoring is non-destructive: whatever is on screen is snapshotted first. Right now that's a Flagstone Foods sheet.)

There's a second, smaller snapshot — *"Unsaved work (no customer selected)", 8/6/2026 9:37:31 AM — 1 day* — which is a single 8/5 Tru Infusion day entered after the reset. The 6-day one is almost certainly what you want.

### 2. Even once saved, the calendar wouldn't have shown it — now fixed

Two bugs meant a newly saved visit could not appear without a full browser reload:

- `App.jsx` `toggleCalendar()` only fetched when `calendarEvents.length === 0`, i.e. **once per page load**. Reopening the calendar reused whatever was fetched the first time.
- The live Firestore subscription (`subscribeAllUpdates`) invalidates caches and calls `loadData()` — which refreshes dashboard stats but **never** `loadCalendarEvents()`. The calendar was outside the refresh path entirely.

**Fixed:** the calendar now refetches whenever it's opened, and the subscription refreshes it too while it's on screen (via a ref, so the once-created callback doesn't read a stale `showCalendar`).

### Also fixed: two UTC date bugs, the same class as the timesheet one

`data-service.js` used `toISOString().split('T')[0]` in two places — that's UTC, so in Arizona (UTC−7) anything after 5pm local lands on the **next day** in the calendar grid:

- `fetchCalendarEvents`, the no-entries fallback that dates a visit by its save timestamp.
- `fetchHeadHistoryData` → `normalizeDate`, which dates every Shearers onsite event.

Both now build the date from local components.

## Security

This is the part that needs attention. The dashboard aggregates **four** Firebase projects, so its effective security is the weakest of the four.

### S1 — The Shearers downtime database is readable by anyone on the internet (verified)

`ShearersClaude/database.rules.json` grants `".read": true` on `jti-downtime/main-logger/data` and `jti-downtime/head-history`. Confirmed live, with no credentials of any kind:

```
GET .../jti-downtime/main-logger/data.json?shallow=true
  HTTP 200 — 5 top-level keys readable: savedAt, data, lockedDays, dates
```

Writes are correctly denied (`PUT` → `401 Permission denied`), so this is disclosure, not tampering. But the whole downtime dataset — customers, lines, notes, machine notes, dates — is public to anyone who knows the database URL, and that URL ships in the JTIUnified bundle. JTIUnified reads this data on every calendar load.

If the intent was to let a share-link viewer read data without logging in, the fix is to expose only the shared slice (there are already `shares` and `shared-views` nodes doing exactly that) rather than opening the whole tree.

### S2 — `JobsMASTER/storage.rules` is a live landmine

```
// WARNING: This allows anyone to read and write.
match /{allPaths=**} {
  allow read, write: if true;   // Public access - anyone can read and write
}
```

That bucket holds `jobs-YYYY.json` — every job, customer, invoice amount and paid status.

**Good news: this is not what's deployed.** Verified — an unauthenticated fetch of `jobs-2026.json` returns `403 Permission denied`. So the live rules are stricter than the file.

**Bad news:** the file is still sitting in the repo, and a single `firebase deploy --only storage` from that folder would publish it and make all of your financial data world-readable *and world-writable* — including deletable. Either bring the file into line with what's actually deployed, or delete it so it can't be deployed by accident.

### S3 — Public self-signup is enabled on all four projects (verified)

Probing `accounts:signUp` on each (deliberately invalid password, so nothing was created):

| Project | Result |
|---|---|
| `timesheetapp-c4e54` | `WEAK_PASSWORD` → signup **open** |
| `downtimelogger-a96fb` | `WEAK_PASSWORD` → signup **open** |
| `jobs-data-17ee4` | `WEAK_PASSWORD` → signup **open** |
| `shearers-4c4b4` | `WEAK_PASSWORD` → signup **open** |

`ADMIN_ONLY_OPERATION` would mean closed. All four are open, and every API key ships in the bundle.

This only bites where the rules trust "any authenticated user":

- **`timesheetapp-c4e54`** — was exactly that; **locked down on 2026-08-05** to an email+uid allowlist.
- **`downtimelogger-a96fb`** (CCW Issues) — fine. Its `firestore.rules` is genuinely well built: role-based, per-customer read isolation, admin checks, expiring share tokens. No action.
- **`jobs-data-17ee4`** — `JTIUnified/firestore.rules` is `allow read, write: if request.auth != null` for everything outside two deliberately-public collections. A stranger who signs up can read and write it.
- **`shearers-4c4b4`** — `auth != null` for writes on `jti-downtime`, so a self-signed-up account can **write** to the downtime tree.

Turning off self-signup in each console is a one-click change and closes most of this.

### S4 — A CCW workspace id is hardcoded in two places

`data-service.js:302` and `:528` both contain `const userId = 'tgezUokMZ1PO7iEDbLbj2U7Uwbx1';`. It works because your account is CCW admin, but it silently breaks for any other login and couples the dashboard to one workspace. It should come from the signed-in user or from config.

## Data loss

### D1 — Deleting a day on the calendar can delete the entire visit

`CalendarView` offers **Delete** with the message *"delete this entry for {customer} on {date}?"*. It calls `deleteTimesheetEntry`, which ends with:

```js
if (updatedEntries.length === 0) {
  await deleteDoc(docRef);          // the WHOLE timesheet document
}
```

Deleting the last remaining day silently destroys the entire visit — customer info, invoice number, machine info, travel, and every service-work note — while the dialog only ever mentioned one day. There is no warning and nothing to undo it. Given the timesheet app now snapshots before every destructive action, this is the sharpest remaining edge in the suite.

### D2 — Delete matches by date, so duplicate dates go together

`entries.filter(entry => entry.date !== entryDate)` removes *every* entry on that date. The timesheet app now keeps one row per date, so this is latent rather than active, but older documents can carry duplicates.

### D3 — Restoring a CCW backup corrupts every customer profile

`backupCCWIssues` stores the raw customer document (which already contains a `profile` field) and hangs `visits` off it. `importCCWIssues` then does:

```js
const { visits, ...customerProfile } = customerData;   // still contains `profile`
await setDoc(doc(...), { profile: customerProfile });  // → { profile: { profile: {...} } }
```

Every restored customer comes back double-nested, so the app can't read its own profile. The backup/restore round trip does not survive a round trip — which is precisely when you need it to.

### D4 — Shearers restore replaces the whole tree with no guard

`importShearers` calls `set()` on `jti-downtime/main-logger/data`, replacing everything under it. No merge, no confirmation, no snapshot of what's being overwritten. `importTimesheet` similarly `setDoc`s each document wholesale. A restore of a stale backup silently discards everything newer.

### D5 — `downloadJSON` revokes its blob URL immediately

`URL.revokeObjectURL(url)` fires on the line after `a.click()`. Some browsers cancel or truncate the download when the URL disappears mid-flight. Every backup export goes through this function.

## Robustness — why failures look like missing data

### R1 — Sign-in to three of the four projects fails silently

```js
const cred = await signInWithEmailAndPassword(auth, email, password);  // CCW only
await Promise.allSettled([
  signInWithEmailAndPassword(jobsMasterAuth, email, password),
  signInWithEmailAndPassword(timesheetAuth, email, password),
  signInWithEmailAndPassword(shearersAuth, email, password),
]);
```

`allSettled` discards rejections. If the timesheet sign-in fails, you are still "logged in" — and every timesheet-backed panel, including the calendar, quietly renders empty.

### R2 — Every fetch swallows its error and returns an empty value

`fetchCalendarEvents`, `fetchTimesheetData`, `fetchInventoryData`, `fetchServiceReports` and others all `catch → console.error → return []`. A permission error, a network drop and a genuinely empty result are indistinguishable in the UI.

**R1 and R2 compound into the exact symptom that started this investigation.** If auth to a project silently fails, the calendar shows an empty month and says nothing was wrong. Surfacing "couldn't reach X" would have made the real cause obvious immediately. This is the highest-value robustness fix in the app.

### R3 — `waitForUser` can hang forever

```js
return new Promise((resolve) => {
  const unsub = authObj.onAuthStateChanged((u) => { unsub(); resolve(u); });
});
```

No timeout, no rejection path. If the callback never fires, `fetchInventoryData` / `fetchPartsManualDiagrams` never settle and their spinners run indefinitely.

### R4 — `fetchServiceReports` does an unbounded N+1 read

One `getDocs` for the customer list, then one more per customer for its visits, all in parallel with no cap. It grows linearly with customer count on every call.

### R5 — Calendar reads the full timesheets collection

`fetchCalendarEvents` pulls every document, entries and all, to build the grid. That was once per page load; with my fix it's once per calendar open. The right long-term shape is a date-indexed summary, not full documents.

## Code quality

- **`App.jsx` is 2,104 lines** with 172 inline `style={{…}}` objects and 21 inline `onClick` closures; `SearchResults.jsx` is 1,465. The inline style objects are rebuilt on every render, so nothing below them can usefully memoize. `CustomerDetailView.jsx` (597 lines) uses no `useMemo`/`useCallback` at all.
- **`devDependencies` is empty.** `vite`, `@vitejs/plugin-react`, `postcss` and `autoprefixer` are all listed as runtime `dependencies`, so a production install pulls the whole build toolchain.
- **Tests cover one file.** `npm test` runs 6 assertions against `utils/format.js` (they pass). Nothing covers `data-service.js` — the date normalisation, the income maths, the service-report join, the delete logic. Note the tests use `node:test`, not vitest; running them with vitest reports a false failure.
- **`formatRelativeTime` is defined twice** — `data-service.js:653` ("5 minutes ago") and `utils/format.js:31` ("5m ago") — with different output. `App.jsx` imports one; `data-service.js` uses the other.
- **Native `alert()`/`confirm()`** in 7 places in `App.jsx` and one in `CalendarView.jsx`, including `confirm('Delete this factory location?')`.
- **`key={index}`** in 16 list renders.
- **Bundle is 1.31 MB** (416 kB gzip) for the main chunk, on top of separate firebase (482 kB) and xlsx (429 kB) chunks. Lazy-loading is already in place for the heavy views, which helps.

## Suggested order

1. **Recover the Tru Infusion work** — ⋯ → Recover unsaved work → the 6-day snapshot → then Save it to the cloud.
2. **S3** — turn off self-signup in all four Firebase consoles. One click each, closes most of the exposure.
3. **S2** — delete or correct `JobsMASTER/storage.rules` before it gets deployed by accident.
4. **D1** — make deleting the last day either refuse or say plainly that it deletes the whole visit.
5. **S1** — narrow the Shearers public read to the shared slice.
6. **R1 + R2** — surface auth and fetch failures instead of rendering empty. This is what turns "my data vanished" into "couldn't reach the timesheet database".
7. **D3 / D4** — fix the backup round trip and put a confirmation in front of restores.
8. **S4**, then the code-quality items as cleanup.
